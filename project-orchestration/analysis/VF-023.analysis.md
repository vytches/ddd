# VF-023 — Analiza: gwarancje strukturalne fundamentów DDD

## Synteza (tech-lead)

Panel (threat-model → library-api-guardian → library-quality-verifier →
tech-lead) rekomenduje **GO** z trzema warunkami bramkującymi:

1. **AC5 + snapshot-capability.ts muszą wejść w tym samym commicie** —
   duck-typing (`_internal_setState?.()`) w snapshot-capability.ts:170-176 musi
   być zaktualizowany równocześnie z gatingiem, inaczej po zmianie cicho nic nie
   zrobi zamiast rzucić.
2. **Model proxy dla AC8 musi być na miejscu przed tagiem release'u** — patrz
   D-6.
3. **Przewodnik migracyjny dla AC1 musi zostać zweryfikowany przez zespół**
   przed publikacją — patrz OQ-2.

### Rozstrzygnięcie: spójność AC1 vs AC6 (miękka ścieżka migracji)

Panel rozważał, czy AC1 (throw w konstruktorze) powinien dostać ten sam typ
przełącznika `strict`/miękki co AC6 (`onMissingHandler`). **Odrzucone.** AC6
działa na konfiguracji POST-konstrukcyjnej — tryb łagodny jest tam bezpieczny.
AC1 działa PODCZAS konstrukcji wewnątrz `super()` — tryb łagodny (catch + warn)
zostawiłby obiekt w niejednoznacznym, częściowo skonstruowanym stanie, co jest
pułapką poprawności, nie tylko breaking change. Wysoki blast-radius (237
agregatów) jest kompensowany przez klarowność i wsparcie (proxy AC8, przewodnik
migracyjny), nie przez ciche przełączanie zachowania.

### Sekwencjonowanie implementacji (rekomendowane grupy commitów)

1. AC1–AC4 + AC2/AC3/AC11 (deep-freeze) — rdzeń napraw niezmienniczych
2. AC5 + snapshot-capability.ts — gating + aktualizacja duck-typingu W TYM SAMYM
   COMMICIE
3. AC6, AC9, AC10 — non-breaking follow-upy

### Korekta względem oryginalnego taska

Task błędnie zakłada, że `VersioningCapability` jest legalnym wywołującym
`_internal_setState` — panel potwierdził grepem, że nie jest (dotyka stanu tylko
przez `handleVersionedEvent` wewnątrz `AggregateRoot.handleEvent`, nigdy
bezpośrednio). Jedynym realnym wywołującym jest `SnapshotCapability`.
