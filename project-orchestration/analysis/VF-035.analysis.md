# VF-035 — Analysis: composite policy step-type coverage gap

## Synthesis (tech-lead)

Three `createPolicyFromStep` switches — `policy-builder.ts:287` (single-step,
5/7 types), `policy-builder.ts:510` (`BuiltCompositePolicy`, 2/7) and
`policy-group.ts:303` (`GroupCompositePolicy`, 2/3) — do not cover the step-type
unions their own sibling public builder methods produce. Real, documented API
usage therefore throws instead of returning `Result.fail(...)`:
`shouldSatisfyAny()` used alone throws at `build()`; any composite mixing
`.mustAsync()`, `.mustSatisfyAsync()`, `.mustSatisfyRules()` or
`.shouldSatisfyAny()` throws at `check()`-time;
`PolicyGroup.must().mustAsync() .getPolicy()` throws at `check()`-time. Root
cause is duplicated switch logic that was never updated as the unions grew. All
affected paths have zero test coverage, and the single existing
`shouldSatisfyAny` test (`policy-builder.test.ts:309`) asserts the broken
behavior.

The agreed fix shape: one shared step-evaluation factory per union in a new
internal (non-exported) file, a new private `OrGroupsPolicy` implementing
OR-over-groups, explicit cases for all union members, and pure `never`-typed
defaults so future union growth fails `tsc` instead of silently reproducing the
bug. Risk: medium (new evaluation class + moderate refactor), mitigated by tight
scope and the regression matrix. Semver: PATCH. Panel verdict: architect design
APPROVED WITH CONDITIONS by the quality verifier (conditions folded into
decisions D2 and D4).

Grounding notes verified directly in code before the panel ran:
`PolicyBuildStep` is a single interface whose `type` field is a 7-literal string
union (narrowing works; exhaustiveness guard is feasible); the 7th member
`'conditional'` is dead — no public method produces it and the interface carries
no payload for it (the fluent `when()` path builds a standalone
`ConditionalPolicy` outside the steps mechanism); `group-or` steps carry
`groups?: IPolicyGroup[]` and no OR-evaluating policy class exists today.

## Implementation plan (ordered work units)

1. **Factory extraction** — new `builders/step-policy-factory.ts`:
   `createStepPolicy<T>(step, id, domain, name)`, the five moved private helper
   policy classes, new `OrGroupsPolicy`, internal `UnsupportedStepPolicy`,
   shared `assertNever`. (~250 LOC, internal only.)
2. **Builder refactor** — both switches in `policy-builder.ts` collapse to a
   single factory call each; file drops well under 400 lines. Behavior for
   existing `specification`/`predicate` paths must be observably identical.
3. **Group factory** — `createGroupStepPolicy<T>` used by both
   `PolicyGroup.createPolicyFromStep` (already complete, becomes a caller) and
   `GroupCompositePolicy` (gains `async-specification`). `never` default in the
   3-member switch.
4. **Tests** — matrix below; invert test at lines 284–316. Group-or tests
   written against the new `shouldSatisfyAny` signature from unit 5.
5. **shouldSatisfyAny return-type fix** (Q4 decision, separate commit) —
   interface + implementation return `IPolicyStepBuilder<T>`; verified
   non-breaking for every documented usage (all chain `.build()` directly).
6. **Verification** — full `@vytches/ddd-policies` suite green, package
   type-check target green, `api-surface.test.ts` snapshot unchanged.

## Required test matrix

1. Single-step `mustAsync(spec).build()` → `check()` returns correct `Result`
   (currently zero calls anywhere in the repo).
2. Composite `must(a).mustAsync(b).build()` → AND-combined `Result`, no throw —
   first-ever exercise of `BuiltCompositePolicy`; add combos for
   `async-predicate` and `rules` steps.
3. Composite `mustSatisfyRules(fn)` + `must(spec)` → no throw.
4. `shouldSatisfyAny(groupA, groupB).build()` alone → **invert existing test
   309**: `build()` must not throw; `check()` succeeds when either group passes;
   when both fail, one `GROUP_OR_FAILED` violation with populated
   `details.groupFailures`.
5. `shouldSatisfyAny` combined with another step (group-or inside
   `BuiltCompositePolicy`) — the exact failure mode from the bug report.
6. `PolicyGroup.create().must(a).mustAsync(b).getPolicy()` → real `check()`
   assertions (existing test only asserts `toBeDefined()`).
7. Regression: existing single-step and `specification`+`predicate` composite
   behavior byte-identical (error codes, violation shape, stepId format
   `${id}_step_${index}`).
8. Exhaustiveness: not runtime-testable — verified by running the package
   type-check target after the change.

## Risks & out-of-scope follow-ups (candidates for separate tasks)

- `logicOperator: 'OR'` set by `PolicyStepBuilder.or()` is ignored by
  `BuiltCompositePolicy`'s pure AND loop — `.or()` is silently broken today
  (latent, distinct from this bug class).
- `BuiltCompositePolicy.check()` recreates step policies on every call (latent
  perf; profile before tasking).
- `policy-builder.test.ts` is a monolith covering builder, group and composite
  scenarios; candidate for a test-file split post-ship.
- Dead `'conditional'` union member (and the dead `'predicate'` members in
  conditional-policy-builder.ts internal step types) — union trimming is a
  separate cleanup, explicitly out of scope here.
