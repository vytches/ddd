## Why

The example-coverage audit (2026-07-03, saved as memory
`project_examples_coverage_audit`) surfaced exactly the problem this task needs
to solve: in 7 packages, README and LLMGUIDE.md have drifted apart (conflicting
API signatures, one example doesn't even compile), because the docs were checked
off by hand without any mechanism forcing them to match the actual code. A
"features × levels × combinations" matrix will suffer the same fate if its cells
are checked off by hand.

The only proven mechanism in this repo that avoids that: `examples/policies/` —
every example file has a matching test in `tests/policies-examples.test.ts` that
actually compiles and runs it. That's the pattern to extend, not reinvent.

On top of that, the user wants verification to go beyond "it compiles" — they
want evaluators that check whether a given package combination is **possible and
sensible** (e.g. does `CircuitBreakerDecorator` on a real `@CommandHandler`
actually behave correctly under retry/backoff, not just type-check). **No
golden-query/eval mechanism exists anywhere in this repo** (confirmed by grep —
zero hits) — this has to be designed from scratch, not wired into something that
already exists.

## Acceptance Criteria

1. [ ] Define the matrix dimensions: 19 packages × levels
       (quick-start/intermediate/advanced) × named combinations — baseline list
       from the audit (aggregate+specification, domain-service+policy,
       CQRS+resilience [decorator and functional], CQRS+specification/
       validator, real transactional unit-of-work, plus combinations already
       confirmed to work).
2. [ ] Baseline mechanism (compile-and-run): a cell is TRUE only if a file under
       `examples/` exists with a CI test that actually compiles and runs exactly
       that scenario — extension of the `examples/policies/` pattern.
3. [ ] Matrix generated by a script from repo state (reads `examples/*/src`
   - associated tests), not a hand-edited markdown file. CI fails on mismatch
     (an example file with no passing test, or a declared-but- nonexistent
     combination).
4. [ ] RESEARCH sub-scope (open question to resolve in /analyze-ddd): an
       evaluator for "is this combination semantically sensible", not just
       syntactically valid. To be determined: sanity criteria (runtime
       assertion? DDD-invariant check? comparison against expected behavior?),
       where the harness should live (extend the existing `packages/testing`
       GWT/seeder framework vs. a new `tools/` package), pilot on 1-2
       combinations from the list in item 1.
5. [ ] Decide where the matrix is published (a generated file under docs/, vs. a
       CI/PR report).

## Out of scope

- Filling in every cell with new examples — that's separate, per-combination
  tasks, to be split out once the mechanism here is settled.
- Fixing the existing README ↔ LLMGUIDE drift (see the audit) — a related topic
  and a precondition for the matrix's credibility, but not part of this task.
